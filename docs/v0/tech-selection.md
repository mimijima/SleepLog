# 技術構成・公開方法の検討

## 目的

v0を実装・公開するために、認証、データ保存、アプリの実行環境、公開方法を選ぶ。

この文書では、選定に必要な条件と採用した構成を整理する。

## v0で満たす条件

### アプリの利用

- ブラウザで利用でき、スマホ・タブレット・PCで同じ機能と操作フローを提供する。
- 複数端末で同じ睡眠記録を扱える。
- 就寝中かどうかを、端末ではなく保存された未完了の睡眠記録から判定できる。

### 認証・アカウント

- メールアドレスとメールで送るコードによるパスワードレス認証を使う。
- v0では、管理者が許可したメールアドレス1件だけが利用できる。
- 新規登録画面は作らない。
- ログイン状態を安全に維持できる。

### データ保存・アクセス制御

- 睡眠記録を永続的に保存できる。
- 睡眠記録は所有者ごとに扱い、他者が閲覧・編集できないようにする。
- 就寝日時・起床日時・未完了状態を保存できる。
- 過去の記録を含むグラフ表示と、追加・編集・削除に対応できる。
- CSV出力などの将来機能を妨げない形で、データを取り出せる。

### 公開・運用

- アプリ本体をHTTPSで公開できる。
- 認証情報、メール送信サービスの設定、管理者用の設定値を、ソースコードや公開リポジトリに含めずに管理できる。
- 利用するサービスに応じたプライバシーポリシーを後から作成できる。

## v0では選定対象にしないもの

次の機能はv0の実装対象外であり、今の技術選定で実装方法を決めない。

- 一般ユーザーの登録・複数ユーザー対応
- 睡眠記録の公開
- CSV取り込み・出力
- AIによる睡眠分析
- 睡眠・1日のコンディション評価

ただし、将来これらを追加できるよう、特定の端末内だけに閉じたデータ保存にはしない。

## 選定する項目

1. Webアプリの開発基盤  
   画面、認証済みの操作、グラフ表示を作るための基盤。
2. 認証サービス  
   メールによるコード送信、ログイン状態、許可するメールアドレスの制限を扱う。
3. データベース・アクセス制御  
   睡眠記録の保存と、所有者以外からのアクセス防止を扱う。
4. ホスティング  
   アプリをHTTPSで公開する。
5. メール送信  
   ログイン用コードを送る。
6. 設定値・秘密情報の管理  
   管理者の許可メールアドレスや各サービスの秘密情報を、公開リポジトリの外で管理する。

## 判断に必要な未決定事項

- v0では、月額1,000円程度までを許容する。
- 睡眠記録を保存する地域・事業者に関する希望
- 独自ドメインをv0から使うか
- 外部サービスへの依存をどこまで許容するか

## 候補の比較

| 候補 | 構成 | v0との適合 | 評価 |
| --- | --- | --- | --- |
| Supabase・Cloudflare・AWSの組み合わせ | Supabase Auth、PostgreSQL、RLS、Cloudflare Pages、AWS SES | メールで届くコードによるログイン、複数端末同期、睡眠記録の保存・所有者ごとのアクセス制御に対応できる。メール送信制限を避けて開発時から動作確認でき、将来も各サービスを継続利用できる。 | 採用 |
| Firebase | Firebase Authentication、Firestore、Firebase Hosting | 認証・保存・公開を一体で扱えるが、標準のパスワードレス認証はメールリンクが中心であり、メールで届くコードを入力するv0の仕様にそのまま合わない。 | 今回は見送り候補 |
| 独自バックエンド | 任意の認証、データベース、ホスティング、メール送信を個別に組み合わせる | 仕様は満たせるが、認証・メール送信・アクセス制御を自分で組み合わせて運用する必要がある。 | v0では過剰 |

## 採用する構成

v0では、次の構成を採用する。

- アプリの公開：Cloudflare Pages
- 認証：Supabase Auth
- ログイン方式：メールで送るワンタイムコード
- メール送信：AWS SESをSupabase AuthのカスタムSMTPとして設定する
- データベース：SupabaseのPostgreSQL
- アクセス制御：SupabaseのRow Level Security（RLS）
- サーバー処理：v0では作らない。ブラウザのJavaScriptがSupabaseのAPIを通じて認証とデータ操作を行う。
- JavaScriptの開発基盤・フレームワーク：現時点では固定しない。実装前に、SleepLogで必要になる役割と違いを確認してから選ぶ。

Cloudflare Pagesは、HTML、CSS、JavaScriptをHTTPSのURLで配信する。睡眠記録とログイン状態はSupabaseで扱う。AWS SESはログイン用のワンタイムコードをメールで送信する。

AWS SESは、開発時には検証済みの自分のメールアドレスへ送信して動作確認する。v1以降に一般利用者へ送信する段階で、SESの本番利用手続きを行う。

公開リポジトリのソースコードには、Supabaseの管理用キーやAWS SESのSMTP認証情報を含めない。Supabaseの公開用キーはブラウザからAPIを利用するために配布物へ含めるが、秘密情報としては扱わず、RLSによってデータアクセスを制限する。

v0では、あらかじめ許可したメールアドレスのアカウントだけをSupabase側に作成し、ログイン時に新規アカウントを自動作成しない設定を使う。

## 採用構成で後から決めること

- Supabaseプロジェクトの保存地域
- AWS SESの送信元メールアドレスと、v1以降に使う送信ドメイン
- Cloudflare Pagesの公開URLと、独自ドメインを使う時期
- JavaScriptの開発基盤・フレームワーク
- Supabase無料プランのプロジェクトが一時停止した場合の、アプリ上の表示と管理者による再開手順
- 将来サーバー処理が必要になった場合に、Cloudflare Workers、Supabase Edge Functions、AWS Lambdaのどれを使うか
