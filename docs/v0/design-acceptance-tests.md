# v0 画面デザイン受け入れテスト項目

## 目的と範囲

この文書では、v0 の画面デザインが、画面仕様と採用したデザイン案に沿っていることを確認する。

- 必要な要素が欠けず、重なったり見切れたりしていないこと
- 文字、日時、グラフ、操作部を無理なく判別できること
- 画面サイズや文字サイズが変わっても、必要な情報と操作へ到達できること
- 同じ役割の要素が、画面間で一貫した見た目になっていること
- 各表示状態が、採用したデザインの意図を保っていること

確認時は、判定IDごとに `OK` または `NG` を記録する。`NG` の場合は、確認環境、実際の表示、期待結果との差を記録する。

確認基準は、[v0 仕様書](./specification.md) と [画面デザイン案 README](../../design/visual-directions/README.md) とする。デザイン画像との完全なピクセル一致は求めず、画面サイズに応じた余白、表示件数、改行などの調整を許容する。機能の成否は [v0 受け入れテスト項目](./acceptance-tests.md) で確認する。

処理中表示や通信失敗表示など、仕様が未決定の状態は、仕様決定後に追加する。

## テスト実施前に必要な作業

現時点の内容は、デザインに関する確認観点を整理したものであり、実際に結果を記録するための最終版ではない。テスト実施前に、次の具体化を行う。

- 対象とする端末、OS、ブラウザ、画面方向、表示倍率を確定する
- B以降の各画面・表示状態を、対象環境ごとのテストケースに展開する
- Aの共通確認項目を、対象環境ごとの各画面・表示状態のテストへ組み込む
- 期待結果を、判定IDごとに迷わず `OK` または `NG` を付けられる粒度まで細分化する
- 操作手順と確認結果が一対一になるように整理する
- 判定結果、実際の確認環境、備考を記録する欄を設ける

上記の具体化が完了するまでは、この文書をテスト観点の洗い出しと漏れの確認に使用する。

## レスポンシブデザインのテスト方法

レスポンシブデザインは、すべての端末と画面状態の組み合わせを同じ深さで確認するのではなく、次の確認を組み合わせてテストする。

1. 全画面を代表的な複数の画面サイズで簡易確認する
2. 画面ごとに崩れやすいと想定した状態を重点的に確認する
3. 主利用端末では、主要な利用経路を最初から最後まで実機で操作する
4. 最後に、数値だけでは判断しにくい読みやすさや全体の違和感を人の目で確認する

### 機械的に判定する項目

次のような項目は、できるだけ担当者の感覚に頼らず、判定IDごとに `OK` または `NG` を付ける。

- 意図しない横スクロールが発生しない
- 文字、画像、ボタン、入力欄が画面外で切れない
- 要素同士が重ならない
- 必要な操作部を確認して操作できる
- スクロールすれば必要な情報と操作部へ到達できる
- 一時表示や確認ダイアログが画面外へ不自然にはみ出さない
- ソフトウェアキーボード表示中も必要な操作へ到達できる
- 固定ヘッダーや下部タブが本文や操作部を隠さない

### 画面ごとに重点確認する項目

仕様とデザイン案から、表示内容の長さや件数によって崩れやすい箇所を事前に想定しておく。SleepLog では、少なくとも次を重点確認する。

- 長いメールアドレスの折り返し
- グラフの日付、曜日、時刻目盛り、睡眠区間の重なり
- 睡眠一覧の長い日時と編集・削除操作部の重なり
- 睡眠一覧の件数が増えた場合のスクロール領域
- 年月選択を狭い画面で開いた場合の収まり
- 日付・時刻入力UIやソフトウェアキーボードを表示した場合の操作部への到達
- 記録画面の背景とロールカーテン部品の位置関係

### 人の目で総合判断する項目

次の項目は完全な数値判定が難しいため、デザイン案と実際の利用場面を基準に人の目で確認する。ただし、単に「好み」や「感覚」で判定せず、NGとした理由を具体的に記録する。

- 余白が狭すぎたり広すぎたりしない
- 文字が読めても、不自然に小さくなっていない
- 主操作と副操作の優先順位を理解できる
- グラフから睡眠の推移を把握しやすい
- 背景と文字の組み合わせが読みやすさと落ち着いた雰囲気を両立している
- 画面間で色、線、アイコン、余白に大きな違和感がない

実施前に、可能な項目は「拡大せず日時を読める」「主操作を迷わず見つけられる」など、実際の画面を見て判定できる表現へ具体化する。

### 確認する画面サイズの選び方

有名な端末サイズだけではなく、レイアウトが崩れやすい境界付近も確認する。

- 想定する最小画面幅
- 主利用端末の画面サイズ
- 一般的なスマートフォンの画面幅
- タブレット
- PC
- レイアウトが切り替わる幅の直前と直後
- 縦方向が短い画面
- 文字を拡大した状態
- 必要に応じて縦向きと横向き

実装で画面構成を切り替える幅を設定した場合は、その直前と直後の両方を必ず確認する。

個人開発の v0 では、すべての環境を同じ深さで確認することは避ける。ブラウザのレスポンシブ表示で複数サイズを確認したうえで、iPhone 15では主要操作を一通り実機確認し、その他の端末では崩れやすい画面を重点的に確認する。

## 確認環境

少なくとも次の環境で確認し、端末、OS、ブラウザ、画面方向、表示倍率を結果と一緒に記録する。

- 主利用端末となる iPhone 15 の縦向き表示
- iPhone 15 より横幅の狭いスマートフォン相当の表示
- タブレットの縦向きまたは横向き表示
- PC ブラウザの表示
- ブラウザの拡大表示または端末の文字サイズを大きくした表示

端末を用意できない場合は、ブラウザのレスポンシブ表示で事前確認し、実機確認時に結果を補完する。

## 前提データ・表示状態

- 画面幅内で折り返しが必要になる程度の長いメールアドレス
- 記録なし、1件、複数件を含むグラフデータ
- 日付をまたぐ睡眠、16:00をまたぐ睡眠、1日に複数回ある睡眠
- 平日、土曜日、日曜日、月をまたぐ期間
- 睡眠一覧が0件、1件、4件、表示領域を超える件数の各状態
- 追加・編集の通常状態と、各入力エラーが表示された状態
- 記録開始前、睡眠中、起床操作中、起床直後の各状態

### A-01 通常表示での画面収まり

**前提条件**：対象画面を表示できる

**手順**：対象の確認環境で、各画面と一時表示を1つずつ開く

| 判定ID | 期待結果 |
|---|---|
| A-01-01 | 意図しない横スクロールが発生しない |
| A-01-02 | 文字、画像、入力欄、操作部が画面外で不自然に切れない |
| A-01-03 | 要素同士が重なって読めなくなったり、操作できなくなったりしない |
| A-01-04 | スクロールが必要な画面では、すべての内容と操作部まで到達できる |

### A-02 文字を大きくした表示

**前提条件**：対象画面を表示できる

**手順**：表示倍率または文字サイズを大きくし、各画面と一時表示を1つずつ開く

| 判定ID | 期待結果 |

| A-02-01 | 主要な文字が途中で切れず、内容を読み取れる |
| A-02-02 | 文字が画像、入力欄、別の文字、操作部と重ならない |
| A-02-03 | 改行や縦方向の拡張後も、必要な操作部まで到達できる |

### A-03 共通操作部の一貫性

**前提条件**：記録画面とグラフ画面を表示できる

**手順**：記録画面、グラフ画面、各画面の右上メニューを順に表示する

| 判定ID | 期待結果 |
|---|---|
| A-03-01 | 右上メニューボタンは、画面間で同じ大きさと基本形状に見える |
| A-03-02 | 下部タブは、画面間で同じ高さと配置に見える |
| A-03-03 | 選択中のタブは、通常のタブと十分に区別できる |
| A-03-04 | 主操作と副操作を、色、濃淡、枠などから判別できる |

### A-04 操作できない要素の見分け

**前提条件**：無効な操作部を含むログイン送信前状態と年月選択状態を表示できる

**手順**：各状態を表示し、有効な操作部と無効な操作部を見比べる

| 判定ID | 期待結果 |
|---|---|
| A-04-01 | 無効な操作部は、有効な操作部と濃淡やコントラストなどで区別できる |
| A-04-02 | 無効な操作部の文字や意味は読み取れる |
